# optimize-app changelog

One line per change: date, kind of repo audited, what changed and why.

- 2026-11-19 · (design change, no audit) · Connected "Project memory" to the workflow (step 2 reads the profile, step 7 saves the report and updates it, step 8 updates finding status, step 10 sends project facts there), allowed the audit to write its own notes and to ask before creating the folder, replaced the profile's Stack, Commands and Guardrails sections with pointers to the repo's own files, and added the worktree rule. Reason: no step used the profile, writing it contradicted the read-only rule, copied facts go stale, and git-ignored notes are absent from worktrees.
- 2026-11-19 · Next.js marketing site · Added: running the project's scripts in an exported copy outside the repo, re-running a failing test alone before reporting it, weighing the HTML document, and per-step CI timings; widened the cross-check (delegated citations, built HTML, existing issues, public-repo wording). Reason: the audit had to work out the exported-copy method itself, nearly reported a load-sensitive test as broken behavior, found 8 KB of repeated inline data per page that the script-only measurement misses, and found a CI step taking a seventh of the run only by reading step timings.
- 2026-11-18 · (design change, no audit) · Added "Project memory": each audit writes `.claude/optimize-app/PROFILE.md` (project facts, updated in place) and a dated report under `audits/`. Reason: project-specific knowledge needs a home that is not this file, and repeat audits need a before/after record without numbered copies of the skill.
- 2026-11-18 · Next.js marketing site; FastAPI + Next.js internal tool · Added the preflight step, read-only safety rules, the "existing guardrails first" rule, the Techniques section (client import tracing, gate checks, dead-code false positives, hot vs cold paths), per-app reports and the "Improve this skill" step. Reason: the first version assumed the project could be built in the audit environment, flagged decorator-registered routes and disk-loaded content as dead code, and treated one-off migrations as hot paths.
